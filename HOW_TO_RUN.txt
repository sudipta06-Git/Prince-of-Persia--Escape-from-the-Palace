HOW TO RUN THE GAME
===================

To play:  double-click  Play.bat   (or  iGame\iGame.exe  directly)

To build: open iGame.sln in Visual Studio 2013, then Build -> Rebuild
          Solution, and press Ctrl+F5. The .exe is written to iGame\ .


WHY IT WOULD NOT START BEFORE
-----------------------------
The build was putting iGame.exe into a Release\ folder at the top level,
on its own. Three things it needs were not there:

  1. GLUT32.DLL - it is not a Windows DLL, so Windows could not find it
     anywhere and refused to start the program at all. That is the
     "cannot start because GLUT32.dll is missing" message.

  2. Assets\ - every picture is opened by a relative path such as
     "Assets/Player/l1.png", so from Release\ none of them existed.

  3. The .mp3 and .wav files, opened the same relative way.

All three live in iGame\ , so the .exe is now built into iGame\ as well
and finds everything beside it.

A second problem was also fixed: iGame\ contained a copy of
opengl32.dll and glu32.dll taken from Windows XP (version 5.1.2600,
dated 2002). Windows loads a DLL sitting next to the .exe in preference
to its own, so the game was being pushed onto a 2002 OpenGL that cannot
talk to a modern graphics driver - which is what made textures come out
white. Windows supplies both of those DLLs itself, so the XP copies were
removed. GLUT32.DLL is NOT one of these - it is not part of Windows and
must stay in iGame\ .


THE CRASH A FEW SECONDS AFTER STARTING
--------------------------------------
Once it started, the game then died within about ten seconds with

    Unhandled exception ... (msmpeg2ac3dec.dll) 0xC0000602:
    A fail fast exception occurred.

msmpeg2ac3dec.dll is the Microsoft DTV-DVD Audio Decoder. The game used
to play each MP3 by opening an MCI "mpegvideo" device, which is really a
DirectShow graph, and on this build of Windows opening a SECOND such
graph while the first is still open makes that decoder kill the whole
process. A fail fast cannot be caught by any error handler. The game
opened four of them during startup: click.mp3, running.mp3, gamebgm.mp3
and wonbgm.mp3.

This was confirmed, not guessed: a 25-line test program that does
nothing but open two of those files the same way dies in exactly the
same place, and opening any one of them on its own is fine.

Opening them one at a time was not an option, because the music has to
keep playing underneath the click and the running loop.

So the MP3s are now decoded once, when they load, through the ACM codec
l3codeca.acm - an older decoder with no connection to DirectShow - and
played through waveOut, which is happy to mix any number of streams.
Same .mp3 files, no new files, same volumes, same looping. All of that
lives in "Header Files\sounds.h"; every function there kept its name and
its behaviour, so no other source file needed to change.


WHAT WAS MOVED, NOT DELETED
---------------------------
Nothing was thrown away. These went into _backup_originals\ :

  _stray_dlls\        the Windows XP opengl32.dll and glu32.dll
  _stale_build_state\ the old Release\ output, iGame\Release\
                      intermediates, iGame.sdf and iGame.v12.suo - all
                      of it generated on a different PC (the build logs
                      still pointed at C:\Users\smart view\...), and all
                      of it regenerated by Visual Studio on the next
                      build.

There is also an iGame\iGame_locked_by_vs.exe. That is the old build.
Visual Studio still had it open as a debug target while the new one was
built, and Windows will not delete a file that is still mapped. Close
Visual Studio and you can delete it; nothing refers to it.

No asset, no sound file, and no game logic was changed. The only source
change is the MP3 playback backend in "Header Files\sounds.h" described
above, which was required to stop the crash.
